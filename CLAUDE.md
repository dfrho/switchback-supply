# Switchback Supply

A LaunchDarkly demo app: a mock eCommerce store (an outdoor gear retailer) that answers LaunchDarkly's Senior Solutions Engineer take-home exercise. The audience is LaunchDarkly SEs reviewing it as if it were delivered to a prospective customer, so **code comments, the README, and PR descriptions are part of the product**. Write them for that reader.

- Part 1, Release and Remediate: `release-new-checkout` wraps the checkout drawer (Classic vs Express), a change listener swaps it live, and a flag trigger turns it off (`npm run remediate`).
- Part 2, Target: `release-landing-hero` wraps the home page hero (current vs Winter-Ready), with shopper contexts, individual targeting, three ordered rules, and a segment.
- Live at https://web-puce-kappa-92.vercel.app (Vercel, Test environment).
- Extra credit, AI Configs: the Trail Guide chat (`web/src/components/ShoppingAssistant.tsx`) posts to `/api/assistant`, where `server/assistant.ts` evaluates the AgentControl config `shopping-assistant` (stable `@launchdarkly/server-sdk-ai` v2), calls Claude with `@anthropic-ai/sdk`, tracks the run, and sends the `assistant-recommended-product` experiment event.
- Next: see `docs/claude/roadmap.md` (rehearse the demo on the live site).

## Commands

| Command | Use |
|---|---|
| `npm run dev` | Storefront on http://localhost:5173 (needs `.env`) |
| `npm run typecheck` | TypeScript, web and tests |
| `npm run lint` | oxlint |
| `npm test` | Vitest unit and component tests |
| `npm run test:e2e` | Playwright; starts a mock LaunchDarkly (8787), dev server (5180), and production preview (5181) itself |
| `npm run build` | Production build to `web/dist` |
| `npm run validate:catalog` | Catalog checks (also in CI) |
| `npm run ld:setup -- --dry-run` | Print the Part 2 LaunchDarkly changes without sending them |
| `npm run ld:setup` | Apply Part 2 flag, segment, and targeting, plus the AgentControl config, variations, and metric, through the REST API (changes the real environment) |
| `npm run remediate` | Fire the real flag trigger that turns the checkout flag off (changes the real environment) |
| `npm run assistant:traffic -- --dry-run` | Plan and cost estimate for synthetic experiment shoppers; without `--dry-run` it makes real, paid Claude calls |

Before opening a PR, run `npm run typecheck && npm run lint && npm test && npm run test:e2e`. CI runs the same, plus a catalog check, a secrets guard, and an `ld:setup` dry run.

## Hard rules

- **Secrets never enter the repo, the browser bundle, or chat.** Only the client-side ID may be a `VITE_` variable. The SDK key, API token (`LD_API_TOKEN`), trigger URL, and Anthropic key are server-side or `.env` only. Do not read or print `.env`; ask the user for any value you need to confirm. CI fails on anything shaped like an SDK key, API token, or trigger URL.
- **Every flag key lives in `web/src/launchdarkly/config.ts`** with a safe fallback in `FALLBACKS`. Browser `track()` event keys live there too, in `METRIC_EVENTS`, with their metric definitions in `scripts/ld-metrics.mjs`. The fallback is always the known-good experience. AgentControl config keys and server-side metric event keys live in `server/config.ts`; the assistant's fallback is disabled (no model call).
- **The assistant's prompts and variations live in `scripts/ld-ai-config.mjs`**; a unit test keeps its keys in step with `server/config.ts`. Prompt facts (like free shipping at $150) must match the store.
- **Changing targeting or personas means changing these places together**: `scripts/ld-targeting.mjs` (what `ld:setup` writes), `HERO_TARGETING` in `config.ts` (Release Console labels), `tests/e2e/fixtures.ts` (mock), and the README's Step 8 targeting table and Part 2 persona table (personas live in `contexts.ts`). A unit test checks the first two stay in step.
- **Commands that change the real LaunchDarkly environment or spend money** (`npm run ld:setup`, `npm run remediate`, `npm run assistant:traffic` without `--dry-run`) run only when the user asks.
- **No emojis and no em dashes** anywhere: code, comments, docs, commit messages, PR text. Use commas, colons, parentheses, or two sentences.
- Prefer plain words in user-facing text. Every LaunchDarkly feature mentioned in the README links to the LaunchDarkly doc page it relies on.

## Git workflow

- One branch and one PR per section or feature (`feat/...`, `docs/...`, `chore/...`), never commit to `main`.
- PR description: what changed, how it meets the brief, how it was tested. Keep the README's status table and test counts current in the same PR.
- **Merge only when the user says "merge"**, as a squash merge titled `<PR title> (#N)`, after CI passes. Earlier PRs (#1 to #5) followed this pattern.

## Gotchas learned the hard way

- **Environment mismatch**: LaunchDarkly client-side IDs start with a creation timestamp, so environments created together (Production and Test) share their first characters. Compare whole IDs. `ld:setup` checks which environment owns `VITE_LD_CLIENT_SIDE_ID` and stops on a mismatch. The app currently uses **Test**; see `docs/claude/launchdarkly-environment.md`.
- **Ad blockers that use the EasyPrivacy list** block `events.launchdarkly.com` (rule `||events.launchdarkly.com^$third-party`; DevTools shows `(blocked:other)`). Verified November 2, 2026: Brave Shields blocked it and a Chrome Incognito control delivered it; uBlock Origin enables EasyPrivacy by default but was not tested. Flags still evaluate (the flag hosts are not on the list); the Event debugger, metrics, and experiment data stay empty. Test in a clean Chrome profile.
- **The dashboard's attribute dropdowns list only attributes LaunchDarkly has received.** Use `ld:setup` (REST API, semantic patch) instead of waiting.
- **Debug targeting from the evaluation response**, not the dashboard: DevTools > Network > filter `withReasons` > `context?withReasons=true` (REPORT) shows `value`, `variation`, `flagVersion`, and `reason` per flag.
- `useReport: true` keeps contexts (including the private email) out of URLs; in browsers the SDK then uses a context-free `/ping` stream and REPORT polls. The mock server supports both modes.
- The `change:<key>` event carries the context, not the value; read the value with `boolVariation`. `identify()` never rejects. Never call `identify` inside a change handler.
- React StrictMode runs effects twice in development; every subscription needs a cleanup that passes the same handler to `off`.
- Vite reads `.env` only at startup (`envDir: '..'`, repo root). Restart `npm run dev` after editing it.
- The repo root is an ES module package (`"type": "module"`): no `__dirname` in root-level TS; server imports use `.js` specifiers. Current Claude models reject `temperature`/`top_p`/`top_k`; only `max_tokens` and `effort` are forwarded from a variation.
- `@playwright/test` is pinned to 1.63.0. On a new machine run `npx playwright install chromium` once.
